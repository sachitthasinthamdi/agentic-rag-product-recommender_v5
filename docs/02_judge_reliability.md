# ความน่าเชื่อถือของ LLM judge สำหรับตัดสิน "ประเภทสินค้าตรงกันไหม"

> สรุปการทดลอง 2026-09-29 · เอกสารนี้เป็นข้อจำกัดเชิงวิธีวิจัยที่ **ต้องอ้างคู่กับตัวเลข
> product-type precision ทุกครั้ง** ทั้งในรายงานและในเล่ม

## ทำไมต้องมีเอกสารนี้

ตัวชี้วัดหลักอันดับ 2 ของ mark5 คือ **product-type precision ≥90%** (ดู `01_objectives.md`)
ซึ่งวัดด้วย LLM judge ถ้า judge ไม่น่าเชื่อถือ ตัวเลขก็ไม่มีความหมาย — และเราพบว่า
**มันไม่น่าเชื่อถือจริง ๆ** จึงต้องบันทึกไว้ให้ชัดว่าเชื่ออะไรได้แค่ไหน

## วิธีตรวจสอบ

- **Ground truth:** Amazon Shopping Queries Dataset (ESCI) — Reddy et al. (2022), arXiv:2206.06588
  label โดยคนจริงของ Amazon (mark4 เคยใช้ชุดเดียวกันตรวจ judge จึงเทียบข้ามรุ่นได้)
- **ตัวอย่าง:** สุ่ม 200 คู่ (50 ต่อ label) เฉพาะ `product_locale = us`
- **การแมป:** `Exact` → ประเภทเดียวกัน · `Complement`/`Irrelevant` → คนละประเภท ·
  `Substitute` → **ตัดออก** เพราะกำกวมสำหรับคำถามนี้ (ESCI นิยามว่า "ใช้แทนกันได้แต่ไม่ตรง
  ทั้งหมด" ซึ่งบางกรณีเป็นประเภทเดียวกัน บางกรณีไม่ใช่)
- **แบ่ง dev/test 50:50** — ปรับ prompt ด้วย dev เท่านั้น รายงานตัวเลขจาก test ที่ไม่เคยใช้ปรับ
- ตัวอย่างใน few-shot **แต่งขึ้นเองทั้งหมด ไม่ได้คัดจากชุด gold** (กัน train on test set)
- Cohen's κ เขียนคำนวณเอง (`eval/pilot/agreement.py`) เพราะ sklearn ถูก Application Control
  บล็อกบนเครื่องนี้ · เกณฑ์ตีความใช้ Landis & Koch (1977)

## ผลลัพธ์ทางการ (ชุด test ที่ไม่เคยใช้ปรับ prompt)

| ตัวชี้วัด | ค่า |
|---|---|
| **Cohen's κ** | **0.246** — *fair* ตามเกณฑ์ Landis & Koch |
| Accuracy | 68.5% (n = 73) |
| Precision | 52.6% |
| **Recall** | **41.7%** |
| ถูกเมื่อ ESCI = `Exact` | **41.7%** |
| ถูกเมื่อ ESCI = `Complement` | 81.8% |
| ถูกเมื่อ ESCI = `Irrelevant` | 81.5% |

## ข้อสรุป 4 ข้อ

### ① judge เอียงไปทาง "ไม่ใช่" อย่างเป็นระบบ
จับของที่ไม่เกี่ยวได้ดี (~82%) แต่ **ปฏิเสธของที่ตรงจริงถึง 58%**
→ **ตัวเลข product-type precision ทั้งหมดที่วัดด้วย judge ตัวนี้ต่ำกว่าความจริง**
ค่าจริงของทั้ง 6 กลยุทธ์ใน `crosslingual_compare.md` สูงกว่าที่รายงานไว้

### ② ปรับ prompt 4 แบบแล้วไม่มีแบบไหนแก้ได้
วัดบนชุด dev ชุดเดียวกันทุกแบบ:

| prompt | ถูกเมื่อ Exact | Complement | Irrelevant | κ (dev) |
|---|---|---|---|---|
| v2 "เทียบคำนามหลัก" | 30.8% | 75.0% | 78.3% | 0.077 |
| v3 ผ่อนปรน (เน้นว่าคำขยายไม่สำคัญ) | 69.2% | 51.9% | 26.1% | 0.077 |
| v4 ลำดับขั้น (ตรวจอุปกรณ์เสริมก่อน) | 19.2% | 92.9% | 87.0% | 0.111 |
| แยกเป็น 2 คำถามแล้วรวมด้วยโค้ด | 12.5% | 96.4% | 95.7% | 0.109 |

**รูปแบบที่เห็นชัด: บีบด้านหนึ่ง อีกด้านก็หลุดเสมอ** โมเดล 8B ถือเกณฑ์สองข้อพร้อมกันไม่ไหว
(เกณฑ์ที่ 1 "อุปกรณ์เสริมไม่นับ" กับเกณฑ์ที่ 2 "คำขยายไม่สำคัญ")
แม้แต่การแยกเป็นสองคำถามให้แต่ละคำถามมีเกณฑ์เดียวก็ไม่ช่วย

### ③ ค่าประมาณแกว่งมากตามชุดตัวอย่าง
prompt v2 ตัวเดียวกันให้ **κ = 0.077 บน dev แต่ 0.246 บน test** (n ≈ 75 ต่อชุด)
→ ช่วงความเชื่อมั่นกว้างมาก **ห้ามอ้างทศนิยมสองตำแหน่งว่ามีความหมาย**
และห้ามเปรียบเทียบ prompt สองแบบที่ต่างกันไม่ถึง ~0.1

### ④ เพดานของวิธีวัดนี้เองก็ไม่ใช่ 1.0
ESCI มี label ที่ไม่ตรงกับคำถามของเราอยู่บ้าง เช่น คำค้น "gucci belts for women"
คู่กับแว่นกันแดด Gucci ถูก label ว่า `Exact` (จับคู่ระดับแบรนด์ ไม่ใช่ระดับประเภทสินค้า)
→ ต่อให้ judge สมบูรณ์แบบตามนิยามของเรา ก็แตะ κ = 1.0 ไม่ได้

## เทียบกับ mark4

| | mark4 | mark5 |
|---|---|---|
| คำถามที่ให้ judge ตัดสิน | relevance แบบให้คะแนน 0/1/2 | binary "ประเภทเดียวกันไหม" |
| κ ที่วัดได้ | 0.267 (fair) | 0.246 (fair) |

**สมมติฐานที่ตั้งไว้ว่า "คำถามที่แคบกว่าน่าจะได้ κ สูงกว่า" — ถูกปฏิเสธ**
ทั้งสองรุ่นติดเพดานเดียวกัน ซึ่งชี้ว่าข้อจำกัดอยู่ที่ **ความสามารถของโมเดล 8B**
ไม่ใช่ที่การออกแบบคำถามหรือ prompt

## ผลต่อการทำงานต่อ

1. **ตัวเลข precision ที่วัดด้วย judge ใช้ "เปรียบเทียบกลยุทธ์กันเอง" ได้** (ทุกกลยุทธ์โดน
   อคติเดียวกัน) **แต่ห้ามอ้างเป็นค่าสัมบูรณ์** และห้ามใช้ตัดสินว่าผ่านเกณฑ์ ≥90% หรือยัง
2. **การวัดผล guardrail ต้องใช้คนตรวจ** บนตัวอย่างที่สุ่มอย่างเป็นระบบ — จะใช้ judge
   ตัวนี้วัดไม่ได้ เพราะ guardrail กับ judge ใช้เกณฑ์เดียวกัน ถ้าวัดด้วยกันเองจะได้ผลลวง
   (circular) ซ้อนกับอคติที่รู้อยู่แล้ว
3. **เป้า ≥90% ใน `01_objectives.md` ยังใช้ได้** แต่ต้องเปลี่ยน "วิธีวัด" จาก LLM judge
   เป็นการตรวจด้วยคน และระบุขนาดตัวอย่างกับผู้ตรวจให้ชัด
4. ทางเลือกที่ยังไม่ได้ลอง (ถ้าจะกลับมาทำ): ใช้โมเดลใหญ่กว่าเป็น judge ·
   ให้คนทำ gold set ของโดเมนเราเองแทน ESCI · fine-tune ตัวจำแนกเฉพาะงานนี้
